# Трансформация RetailCore: проверяемое промежуточное состояние

Предлагается инкрементальная эволюция: сначала сделать зависимости и состояния наблюдаемыми, затем вынести внутреннее чтение истории заказа. Это первый кандидат на production-переход, а не обещание запустить его к концу третьего месяца. Трёхмесячный результат — проверенная диагностика, границы, критерии и готовность к безопасному пилоту. Основания: E00–E07 в [реестре источников](../sources/README.md); неизвестные параметры — [G01–G16](../Task1/requirements.md).

## 1. Выбор направления и альтернативы

| Вариант | Польза | Цена и риск | Решение |
|---|---|---|---|
| Полная перепись и одновременная смена Oracle | Чистые границы на новой платформе | Неизвестные PL/SQL, канальные исключения и ручные обходы; большая миграция данных и невозможность простого отката | Не подходит C01/C05 |
| Только техническая модернизация монолита | Меньше deployment-границ; полезны modularization и characterization | Shared tables и разные трактовки статусов остаются; независимое чтение не появляется | Использовать внутри ядра, но не как единственный шаг |
| Сразу выделить payment/checkout или владельца всех статусов | Устраняет значимый coupling | Меняет денежные/партнёрские эффекты при неизвестных transaction/retry/consistency правилах | Отложить до G04/G07/G13 и отдельного решения |
| Только Oracle read replica | Может разгрузить часть SQL | Наличие/стоимость/лицензии неизвестны, сохраняются schema coupling и неоднозначная семантика; replica не восстанавливает отсутствующую историю | Возможная тактическая мера после измерений, не целевая граница |
| Наблюдаемость + read-only проекция поддержки | Проверяет capture, контракты и новые storage без смены владельца заказа; возврат чтения обратим | Нужны capacity, свежесть, покрытие writers, защита данных и сверка | Выбран первый кандидат T01–T03 |

Здесь Strangler Fig применяется к пути чтения: небольшой фасад направляет выбранный внутренний экран в старый или новый контур. CQRS — разделение производного чтения и существующих команд. Это **не Event Sourcing ядра**: технические изменения строк не становятся автоматически полным потоком бизнес-событий. Микросервисы выделяются только при подтверждённой ответственности и пользе; число сервисов не критерий успеха.

## 5. Контракты и данные нового чтения

Предлагаемый read API: `GET /internal/support/orders/{orderId}/history` с авторизацией роли и области заказа; версия контракта фиксируется до пилота. Ответ содержит `orderRef`, `aspects`, `observations`, `coverage`, `sourceCheckpoint`, `capturedAt`, `mappingVersion`, `freshness` и причины неизвестности. Пагинация истории должна удерживать согласованный checkpoint. Отсутствие заказа в ограниченной проекции не означает его отсутствия в RetailCore: API различает `not_in_scope`, `not_yet_projected`, `source_not_found` и техническую недоступность. Конкретные коды/схема согласуются с UI в G16.

| Объект | Содержание и владелец |
|---|---|
| Capture checkpoint | Источник/инкарнация БД, позиция и transaction ID; capture-компонент владеет progress, DBA — доступом и источником |
| Durable observation | Source identity, entity key, операция, разрешённые поля, commit position/ordinal, transaction boundary, schema version; не утверждает бизнес-смысл строки |
| Normalized observation | Ссылка на source evidence, raw state + mapping version, order/payment/shipment/item аспект; нормализатор не придумывает недостающий переход |
| Read projection | Текущее наблюдаемое состояние и доступная история, coverage начала наблюдения и известных gaps; владелец — команда заказов совместно с поддержкой |
| Audit доступа/действий | Read audit в новом контуре; действие оператора выполняется и проверяется в legacy. PII/retention — G10 |

PostgreSQL-совместимое хранилище предлагается как кандидат для проекции и durable journal благодаря транзакциям, уникальным ключам и знакомой реляционной модели. Это не решение о всей DWH или замене Oracle. Продукт, HA, объём истории и размещение подтверждаются G02/G06/G10/G11/G14. Journal и read tables могут стартовать в одном одобренном инстансе с отдельными схемами/ролями; границы backup, quota и конкуренция writer/projector должны быть проверены. Отдельный брокер не является обязательным до оценки существующего async-контура; Kafka из кейса AdScale сюда не переносится автоматически.

### Bootstrap и непрерывность

1. DBA и владельцы подтверждают полный для scope набор tables/writers, транзакции, PK, удаления, DDL и чувствительные поля. Outbox только в Java-методе не покрывает прямые batch/admin/.NET writers.
2. Проверяют возможность согласованного snapshot на позиции `S` и commit-aware capture, доступность исторических версий, retention логов, права и лицензии. Oracle SCN/flashback/log mining — кандидаты, а не известная возможность текущей установки.
3. До snapshot запускают удержание change feed. Коннектор должен учесть транзакции, начавшиеся до `S`, но завершившиеся после `S`: сам SCN без такого механизма недостаточен. Копируют ограниченный scope на `S` с backpressure по Oracle guardrail.
4. Сохраняют snapshot и затем применяют committed изменения после `S`, включая поздно завершившиеся транзакции. Capture checkpoint продвигается только после durable записи журнала; projector checkpoint — в одной транзакции с idempotent обновлением read-model. Дубликаты допустимы, уникальный source change ID препятствует повторному эффекту.
5. Порядок внутри источника задают commit/transaction/ordinal, а не несинхронизированные wall clocks. Целостность изменений одной captured transaction сохраняется; независимые источники имеют собственные watermarks, а не фиктивный глобальный порядок.
6. Если обнаружены разрыв, неизвестный writer/schema, неполный snapshot или недоступные логи, projection помечается incomplete, переключение блокируется; нельзя молча перейти к latest position. План восстановления — повторный bounded snapshot/replay по согласованной процедуре.

Если CDC непригоден, рассматривается ограниченная версионированная выгрузка с документированной границей и freshness. Она может дать snapshot состояния, но не доказывает полную историю и не подходит исходному пилоту без пересогласования scope/критериев. Такая развилка меняет план явно.

### Свежесть, отказ и ручные действия

UI показывает, на какой момент и из каких источников подтверждён каждый аспект. Freshness оценивается по end-to-end watermark/heartbeat источника; отсутствие новых событий само по себе не признак свежести. Измерения с разными часами требуют контроля clock skew. `CONFIRMED`, созданная payment session и paid представлены отдельно; если платёжный факт не доступен в согласованном capture scope, он помечается неизвестным.

При stale/incomplete данных запрещено давать оператору ложное подтверждение. Допустимое поведение — маркировка и ссылка на разрешённый legacy read либо ограниченное degraded-представление; выбор и пороги утверждаются G05/G12. Никакой синхронный «ремонт» проекции через write-вызов в заказ. Перед ручной командой старый action handler заново проверяет authoritative state; ссылка из read-view не заменяет эту проверку.

## 6. Схема и предел первого этапа

[TO-BE drawio](to-be.drawio) · [PNG](to-be.png). Зелёный контур — первый кандидат на изменение, серый — сохраняемый, пунктир — последующие шаги или неутверждённые границы. Диаграмма показывает логические ответственности, не гарантированное число deployment units.

Платежи, итоговая цена/промо, резервы, routing и write state machine остаются в ядре из-за необследованных правил, транзакций и внешних эффектов. Для них нужны characterization, партнёрские контракты и самостоятельный migration design. Через год возможны персонализация и новые предложения через согласованные read/extension контракты; G15 пока не позволяет выбирать их алгоритмы, хранилища, SLA или обещать полное извлечение монолита.
