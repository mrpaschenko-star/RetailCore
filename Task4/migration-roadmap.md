# Roadmap управляемой миграции

План основан на [T01–T06](../Task3/transformation.md) и [реестре G01–G16](../Task1/requirements.md). Этапы идут по зависимостям и критериям готовности. Распределение работ внутри первых трёх месяцев — предложение для планирования; оно не заменяет неизвестные staffing, budget и capacity (G14). Бизнес продолжает выпускать изменения; для затронутых таблиц/контрактов вводится согласование совместимости, а не годовая заморозка.

## Этапы, состояния и gates

Зависимости: `R0 → R1 → R2 → R3 → R4 → R5`. Сбор партнёрских контрактов T05 и технологический inventory T06 можно вести параллельно R1–R3 при наличии людей. Write-cutover R6 не является автоматическим следствием успешного чтения. M3 — контроль результата диагностики, а не безусловная дата включения production traffic.

## Что сохраняется и как выпускаются изменения

На R0–R4 единственные исполнители создания заказа, цен/промо, резервов и платежей остаются в монолите/существующих интеграциях. Новому контуру выдаются только необходимые source-read/capture права; обратной записи в source tables нет. Обычные features проходят прежний release flow с добавленной проверкой влияния DDL/статусов на capture/mapping.

Для source schema и контракта проекции применяются совместимые расширения до удаления полей: старая и новая версии читают одно изменение; mapping version хранится в результатах; смена schema требует тестов на representative cases. Если совместимость не доказана, соответствующий canary приостанавливается, а не блокируется весь бизнес-релиз без оценки.

На R5 нельзя удалить legacy read-path, пока он нужен для других каналов, действий или rollback. Сначала проверяются logs потребителей и ownership, затем согласуется retention/recovery period; период неизвестен и должен быть задан владельцами. Удаление таблиц Oracle — отдельное решение после исчезновения всех writers/readers и проверки архива/restore.

## Управление рисками и эффектом

| Риск | Ранний сигнал | Действие / владелец |
|---|---|---|
| Неизвестный writer, gap или DDL | Необъяснимое расхождение / checkpoint discontinuity | Stop projection rollout, сохранить evidence, инвентаризировать и rebuild scope; DBA + техлид |
| Истощение DC/Oracle | Guardrail по DB time/IO/latency/headroom нарушен | Остановить backfill/shadow, не повышать cohort; инфраструктура + DBA |
| Ошибочная семантика оплаты/поставки | Read-view подтверждает факт без authoritative evidence | Откатить чтение, исправить mapping и cases; финансы/логистика + support |
| Нехватка команды/закупка | Нет owner/on-call или доступного approved storage | Сузить первый scope, сохранить диагностику M3; IT + спонсор |
| Сложный rollback | Старый reader/версия недоступны либо не держат fallback | NO-GO до репетиции или согласованного ограниченного degraded mode; эксплуатация |
| Технологическая замена не отвечает политике | Нет approved list/поддержки/лицензий | Не фиксировать продукт как утверждённый; IT + ИБ + закупки |

Эффект оценивается по сопоставимым сценариям до/после: время разбора кейса поддержки, доля ручных межкомандных уточнений, стоимость выбранных Oracle SQL, change lead time. Учитываются канал, сезонность и сложность обращения; простое улучшение среднего без состава выборки не доказывает эффект. Численные цели и стоимость программы согласуются через G08/G14, а не выводятся из общих пожеланий.

## Свидетельства для принятия этапа

В change record хранятся scope, версии source/mapping/API, результаты проверок, значения согласованных порогов, владельцы решения и открытые ограничения. Для R3/R4 обязательны snapshot/checkpoint manifest, отчёт сверки, нагрузочный профиль, restore/rollback rehearsal и журнал маршрутизации. Это список будущих доказательств; текущая учебная работа не утверждает, что production-испытания уже состоялись.
