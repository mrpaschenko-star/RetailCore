# Стенограмма интервью 3 — Разработчик аналитики и отчётности

**Роль:** Senior Python Developer команды аналитики и отчётности  
**Участники:** Архитектор, Максим (разработчик аналитических сервисов)  
**Формат:** интервью  
**Длительность:** ~48 минут

---

**Архитектор:** Как выглядит аналитический контур с твоей стороны?

**Максим:** С точки зрения бизнеса кажется, что у них есть “отчёты по заказам”. С технической точки зрения это набор разношёрстных пайплайнов. Часть данных приходит напрямую из Oracle, часть — из выгрузок монолита, часть — из вспомогательных таблиц, часть — из сервисов, которые позже появились вокруг ядра.

**Архитектор:** То есть аналитика не сидит на едином событийному потоке?

**Максим:** Нет. И это одна из проблем. Было несколько попыток выстроить что-то ближе к событийной модели, но до конца не дожали. Поэтому для части отчётов у нас почти real-time обновление, а для части — ночная или почасовая загрузка.

**Архитектор:** Какие данные самые проблемные?

**Максим:** Всё, что связано со статусами заказа, скидками и фактической логистикой. Потому что эти вещи меняются в нескольких местах, иногда с задержкой, иногда с ретроактивными корректировками. Один и тот же заказ может выглядеть по-разному в зависимости от того, откуда ты его читаешь и в какой момент времени.

**Архитектор:** У вас есть canonical model заказа?

**Максим:** Формально нет. Есть несколько “почти канонических” представлений. Одно ближе к операционному контуру, другое — к финансовой аналитике, третье — к маркетинговым отчётам. И все они чуть-чуть разные.

**Архитектор:** Это создаёт конфликты с бизнесом?

**Максим:** Постоянно. Например, маркетинг говорит одну цифру по выручке кампании, финансы — другую, операционный блок — третью. А потом выясняется, что они брали данные из разных витрин и по-разному трактовали отмены, возвраты и промо.

**Архитектор:** Почему так трудно это унифицировать?

**Максим:** Потому что источник сам по себе неоднозначный. В монолите нет одной чистой модели событий, которую можно просто взять и стримить. Есть текущая таблица заказа, есть история статусов, есть служебные таблицы, есть batch-коррекции. Иногда аналитике приходится восстанавливать смысл задним числом.

**Архитектор:** Как вы забираете данные?

**Максим:** По-разному. Для части отчётов — прямые SQL в Oracle. Для части — выгрузки в staging. Для части — Python jobs, которые забирают данные из API сервисов. Есть ещё старые задания, которые читают CSV, сформированные другими системами. Красоты там немного.

**Архитектор:** Насколько это влияет на производительность основной системы?

**Максим:** В пиковые окна — заметно. Особенно когда тяжелые отчёты или исторические выборки попадают на ту же Oracle, где живёт операционный контур. Нам уже несколько раз просили ограничивать окна выгрузки, потому что операционная база начинала “чувствовать” аналитическую нагрузку.

**Архитектор:** Есть ли проблемы с качеством данных?

**Максим:** Да. Дубликаты, рассинхрон статусов, запаздывание отдельных атрибутов, неочевидное происхождение некоторых полей. Например, поле “итоговая скидка” в одном отчёте может быть взято из итогового расчёта заказа, а в другом — пересчитано аналитическим пайплайном.

**Архитектор:** А lineage? Можно проследить путь поля?

**Максим:** Только местами. Для новых пайплайнов — да, для старых — скорее через людей. Есть участки, где единственный способ понять происхождение — спросить, кто это писал два года назад.

**Архитектор:** Что бы ты назвал главным архитектурным риском в аналитике?

**Максим:** Зависимость от операционной Oracle и отсутствие нормализованного потока событий по заказу. Пока это не решено, аналитика будет постоянно догонять реальность, а не наблюдать её.

**Архитектор:** А что можно делать поэтапно?

**Максим:** Сначала выделить единый набор бизнес-событий заказа и доставки. Даже не всю аналитику строить заново, а хотя бы договориться о каноническом слое событий. Потом уже переводить отчёты и витрины на него. Второй шаг — убрать наиболее тяжёлые выгрузки из операционной базы.

**Архитектор:** Есть ещё что-то, на что студент должен обратить внимание?

**Максим:** Да. Проблемы аналитики здесь — не “только про аналитику”. Они хорошо подсвечивают архитектурные дефекты операционного контура: дублирование логики, отсутствие единой модели статуса, сильную связность с БД и слабую управляемость данных.

---

**Наблюдения, которые можно извлечь из интервью:**
- Нет единой канонической модели заказа для аналитики.
- Один и тот же бизнес-объект интерпретируется по-разному в разных витринах.
- Аналитический контур напрямую зависит от Oracle операционной системы.
- Источники данных неоднородны: SQL, staging, API, batch, CSV.
- Есть проблемы качества данных и слабая прослеживаемость происхождения полей.
- Аналитические проблемы отражают архитектурные проблемы основного контура.
