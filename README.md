# RetailCore — диагностика и поэтапная трансформация

Проектная работа Sprint 4.

Цель первых трёх месяцев — восстановить фактическую картину платформы и подготовить управляемую трансформацию. Годовой ориентир — возможность развивать персонализацию, предложения и партнёрские сценарии без полной переписи критичного order flow.

Решение опирается на пять предоставленных интервью, Java-фрагмент и исходную PlantUML-схему. [Реестр источников](sources/README.md) содержит ограничения доказательности; копии, URL и checksum сохранены в `sources/`. Работа не включает настоящие интервью, доступ к production или измеренные SLA.

## Принятое направление

Сначала инвентаризация writers/readers Oracle, сценариев исключений и наблюдаемость. Затем — согласованный словарь наблюдаемых состояний, надёжный сбор изменений и **внутренняя read-only проекция истории заказа для поддержки**. Она показывает источники, причины, неизвестность и свежесть данных; не управляет заказом и не подтверждает оплату по факту создания сессии. Следом можно переносить выбранные отчёты и изолировать один проверенный интеграционный сценарий.

Создание заказа, итоговая цена/промо, платёжная оркестрация, выбор доставки и операционный Oracle остаются в монолите на первом этапе. SQL/PLSQL, batch и административные вмешательства учитываются до извлечения функций. Переход с Oracle начинается с новых производных хранилищ и явных контрактов; полная замена БД не обещана к произвольной дате.

Нагрузки, latency, SLA/SLO, RPO/RTO, допустимый lag и правила деградации во входных материалах не заданы. Их не подменяют проектными числами: [реестр G01–G16](Task1/requirements.md) фиксирует владельцев и решения, которые нельзя принимать без ответов. Roadmap содержит предлагаемый порядок и gates, а не фиктивно согласованный бюджет или календарь production-переключения.
