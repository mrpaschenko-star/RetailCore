# Сценарии будущих интервью

Это подготовленные сценарии, не стенограммы состоявшихся встреч. [Анализ уже предоставленных материалов](interview-analysis.md) используется для проверки гипотез, но не заменяет новые вопросы. Для каждого ответа записываются источник/пример, область применимости, противоречие, владелец решения и следующий артефакт.

## 1. Бизнес-спонсор

**Цель:** выбрать проверяемую бизнес-ценность первого этапа, допустимые ограничения и правила принятия риска. Гипотезы: H01 — предпочтителен последовательный путь с ранней ценностью; H02 — любые изменения статусов должны защищать обещание клиенту; H03 — непрерывность и коммерческое развитие важнее одномоментной миграции с Oracle. E01 поддерживает эти гипотезы качественно; количественные границы отсутствуют.

| Вопрос | Какую гипотезу / пробел проверяет | Критерий ценного ответа |
|---|---|---|
| Какой эффект через три месяца вы готовы принять: доказанная диагностика, снижение ручной работы, готовый пилот? Что обязательно, а что условно? | H01, C05 | Разделены обязательный результат discovery и optional production-изменения, назван owner приёмки |
| Как ранжировать конверсию, цену изменения, прозрачность статусов и импортонезависимость при конфликте? Приведите решение из прошлой кампании | H02/H03 | Явный trade-off и пример, а не «всё одинаково важно» |
| Какие операции должны сохраняться при деградации, что допустимо показать клиенту и оператору? | G01/G04/G05 | Матрица функций/режимов и согласующий владелец; отсутствие значения зафиксировано |
| Какая потеря заказов/подтверждений недопустима и кто решает вопрос восстановления? | G06 | Назван RPO/RTO owner и область данных, не общая фраза «всё сохраняем» |
| По каким классам изменений измерить lead time и сколько команд обычно участвует? | G08 | Реестр comparable изменений, даты и источник baseline |
| Как измерить эффект снижения ручных контактов без обещания сокращения ФОТ? | G08 | Источник AHT/escalations, метод расчёта и различие capacity/cash effect |
| Что означает отказ от зарубежных компонентов: лицензии, юрисдикция, код, поддержка, конкретный список? | G11 | Утверждённые критерии и сроки или ответственный за них |
| Какие новые сервисы реально должны запуститься через год и на каких данных? | G15 | Приоритетные user journeys, владельцы и зависимости, а не лозунг «экосистема» |
| Кто может остановить pilot/cutover и по каким признакам? Какие инвестиции доступны? | G12/G14 | Назначены полномочия, доступный бюджет/команда либо срок их определения |

**Выход:** согласованные бизнес-критерии этапа, список запрещённых ухудшений, backlog G-пробелов с владельцами. Не превращать просьбу «быстрее» в самостоятельно выбранный процент улучшения.

## 2. Руководитель заказов и оформления

**Цель:** восстановить реальный жизненный цикл, канальные ветки и операционные исключения. Гипотезы: H04 — общий статус не описывает все shipment/payment состояния; H05 — ручное восстановление необходимо для части заказов; H06 — формально подтверждённый заказ ещё не означает подтверждённые оплату и доставку.

| Вопрос | Что проверяется | Критерий ценного ответа |
|---|---|---|
| Проведите по реальному заказу каждого канала: что было обещано и какой факт делает его подтверждённым? | H06/G04 | Примеры IDs с доступом по правилам ИБ, state transitions и источник каждого факта |
| Где отличается поток marketplace, mobile и web; какие ветки нельзя считать эквивалентными? | C06/G02 | Матрица вариантов, не только happy path |
| Как отличить payment session created, authorised, captured, failed, refunded? | H06/G04 | Согласование с платежами; отсутствие правила не заменено mapping по названию |
| Как отражаются split shipment, частичная отмена/наличие и изменение срока? | H04 | Гранулярность item/shipment/order и правила свёртки с примерами |
| Когда заказ уходит в manual review и кто может его вернуть? Что изменяет оператор? | H05/G13 | Перечень UI/API/batch actions, права, audit и эффект на следующие jobs |
| Как узнают об исходе timeout внешнего вызова, когда разрешён повтор? | G07 | Callback/query/reconciliation contract и бизнес-ключ, а не «ретраим» |
| В каком случае клиенту можно показать unknown/stale/pending? | G04/G05 | Согласованные UX-состояния и пороги либо владелец незакрытого вопроса |
| Какой внутренний экран можно переключить только для чтения, сохранив команды в legacy? | A01/G12/G16 | Названы endpoint, группа пользователей, feature flag и зависимости |
| Какие метрики докажут, что новое чтение не ухудшило работу и действительно помогло? | G08 | Cohort/time alignment, разметка расхождений, операторская приёмка |

**Выход:** каталог сценариев и исключений, glossary фактов, карта writers и разрешённый scope support pilot. После интервью — walkthrough с поддержкой/платежами/логистикой; спорные термины не утверждает одна команда.

## 3. Техлид монолитного ядра

**Цель:** доказать технические границы и безопасный способ наблюдения; не выбирать extraction по имени Java-класса. Гипотезы: H07 — оркестрация остаётся в ядре, а Oracle участвует в исполнении бизнес-логики; H08 — shared tables и batch создают скрытые writers; H09 — производное чтение может упростить разбор заказа и снять часть нагрузки; H10 — граница транзакции метода не установлена по фрагменту.

| Вопрос | Что проверяется | Критерий ценного ответа |
|---|---|---|
| Где фактически начинается/завершается транзакция `createOrder`, какие репозитории участвуют в ней? | H10/G13 | Аннотации/config/call chain и trace; не догадка по отсутствию `@Transactional` в примере |
| Кто ещё пишет ORDERS, историю статусов и INT_ORDER_EXPORT? Есть ли triggers/jobs/ручной SQL? | H08/G13 | Полный реестр writer → table/field → transaction → owner |
| Что означает пустой Optional promo? Как обрабатывается exception/timeout и как сравниваются fallback-цены? | H07/G04 | Реализация adapter/catch-path и бизнес-подтверждение семантики |
| Может ли .NET обработать staging-запись до manual review/доставки/оплаты? | H08/G07 | Transaction visibility, consumer contract, пример заказа, фильтры и dedup |
| Какие packages/SQL нельзя перенести простым копированием таблиц Oracle? | H07/G11/G13 | Dependency graph, типы/последовательности/SQL semantics, тестовые fixtures |
| Какие данные можно согласованно снять на SCN, хватает ли log retention и лицензий для CDC? | A02/G13 | POC без пропусков, схема checkpoint, DBA access/impact и recovery |
| Как сейчас измеряются latency, waits, connection pool saturation и внешние зависимости? | G02/G03 | Trace/metrics с каналом и order correlation; sampling/privacy согласованы |
| Можно ли вернуть старое чтение после canary без перегрузки Oracle? Где routing и кеши? | G03/G16 | Измеренный fallback capacity, staging rehearsal и runbook команды |
| Что рискованнее трогать первым и какой seam можно проверить без записи в legacy? | H09 | Обоснование по зависимостям и конкретный regression dataset |

**Выход:** проверенная карта зависимостей, перечень неподтверждённых границ, результаты POC и технические gates. Все команды/версии cutover берутся из реальной конфигурации позднее, не придумываются в архитектурном документе.
