# Требования, ограничения и архитектурные пробелы

Обозначения [источников E00–E07](../sources/README.md) действуют во всех заданиях. Приоритеты P0/P1 ниже — предложение архитектора для обсуждения: P0 защищает текущее выполнение заказа, P1 снижает стоимость развития и открывает новые сценарии. Численных SLO источники не содержат.

## Функциональные требования

| ID / приоритет | Требование | Статус / основание | Архитектурное следствие и способ проверки |
|---|---|---|---|
| F01 / P0 | Сохранить оформление заказа, цену/промо, оплату и доставку во время перехода | Подтверждено E00/E01 | Один владелец каждого write-сценария; characterization tests по каналам; сравнение поведения до изменения |
| F02 / P0 | Объяснять, где заказ, какой следующий шаг известен и почему произошло отклонение | Подтверждено E02 | История с источниками и причинами; неизвестность отображается явно, будущий шаг не предсказывается без правила |
| F03 / P0 | Учитывать manual review, повторную оплату, отмены/возвраты, split shipment и задержанные подтверждения | Подтверждено E02–E04 | Матрица исключений, гранулярность shipment/item/payment; единый плоский статус недостаточен |
| F04 / P0 | Сохранять доступные операторам способы восстановления заказа до их замены | Выведено из E02/E03; полный перечень — пробел | Read-view не переносит команды в новую БД; аудит actions и permissions, инвентарь до cutover |
| F05 / P1 | Согласовать значения статусов и показателей между операциями, финансами, маркетингом | Подтверждено E01/E05 | Версионированные определения, lineage и сверка одной когорты/момента; не выдавать разные срезы за ошибку |
| F06 / P1 | Подключать новые каналы и партнёрские варианты с меньшим числом скрытых зависимостей | Подтверждено E00/E01 | Канальные варианты явно входят в контракты и сценарии; изменение канала не требует автоматической полной декомпозиции |
| F07 / P1 | Подготовить персонализацию и гибкие предложения в годовом горизонте | Подтверждено E00/E01; детали — пробел | Сначала read-контракты и безопасные extension seams; правила персонализации/данные/согласия уточняются |
| F08 / P1 | Поэтапно уменьшать прямую зависимость отчётов/интеграций от Oracle | Подтверждено E00, E03–E05 | Инвентаризация таблиц и PL/SQL; выбранные read consumers переводятся первыми |

## Архитектурно значимые качества

| ID / приоритет | Сценарий качества | Что подтверждено | Чего не хватает / владелец | Как измерять |
|---|---|---|---|---|
| Q01 / P0 | Во время изменения ключевые операции продолжаются | E01 запрещает остановку бизнеса | SLA, downtime и перечень критичных функций — G01, бизнес + эксплуатация | Ошибки, доступность и бизнес-успех по функциям/каналам |
| Q02 / P0 | На сезонном пике checkout остаётся предсказуемым | E01/E03/E05, качественно | Профиль RPS/TPS, p95/p99, объёмы и headroom — G02/G03 | Latency и ошибки вместе с нагрузкой и Oracle wait events |
| Q03 / P0 | Повтор/timeout внешнего вызова не ухудшает заказ скрытым дублем | Дубли логистики E04; последствия E02 | Идемпотентность, timeout/retry и сверка у партнёров — G07 | Дубли бизнес-операций, unresolved outcomes, сверки |
| Q04 / P0 | История объяснима, показывает неполноту и запаздывание | E02/E03/E05 | Допустимые lag, stale UI и сроки эскалации — G04/G05 | Coverage, end-to-end freshness, доля необъяснимых расхождений |
| Q05 / P0 | Данные восстанавливаются после отказа/ошибки миграции | Необходимость выведена из критичности E00/E01 | RPO/RTO, backup/restore, fault model — G06 | Замер restore и фактической потери; не обещать нулевой RPO |
| Q06 / P1 | Типовые изменения требуют меньше времени и межкомандных согласований | E01 | Baseline/целевое сокращение и классы изменений — G08 | Lead time, количество команд/откатов на comparable change |
| Q07 / P1 | Аналитика меньше конкурирует с транзакциями | E05, без измерений | Нагрузка конкретных запросов и приоритет отчётов — G09 | DB time/IO на запросы и freshness выбранного отчёта |
| Q08 / P0 | История и ручные действия доступны только разрешённой роли | Архитектурный вывод; точная политика отсутствует | PII, ACL, аудит, retention и residency — G10 | Проверки доступа/редакции полей; неизменяемый audit действий |
| Q09 / P1 | Технологическую зависимость можно уменьшать без простоя | E00/E01 | Что именно означает импортонезависимость — G11 | Удалённые DB-couplings и закрытые зависимости; не число сервисов |

## Ограничения и допущения

| ID | Тип | Формулировка / основание |
|---|---|---|
| C01 | Подтверждённое бизнес-ограничение | Нет окна для большой одномоментной миграции, развитие нельзя заморозить на год (E01) |
| C02 | Подтверждённое текущее состояние | Java + Oracle, Python/.NET вокруг; Oracle содержит PL/SQL и интеграционные таблицы (E00/E03/E06) |
| C03 | Подтверждённое текущее состояние | Собственный DC, физические серверы, ограниченная виртуализация, ресурсы близки к пределу (E00). Это не доказательство запрета на облако |
| C04 | Подтверждённое текущее состояние | Десятки TB истории, частичное архивирование; точных объёмов/периодов нет (E00) |
| C05 | Подтверждённые горизонты | Через три месяца нужна достоверная диагностика и основа перехода; через год планируются новые сервисы (E00). Полная замена ядра за три месяца не требуется |
| C06 | Подтверждённая неоднородность | Разные каналы, исключения, ручные и batch writers; схема E07 неполна (E02–E05) |
| A01 | Допущение для проектирования | Для первого пилота можно выбрать внутреннее read-only представление поддержки. Это предложение, требует владельца и проверки нагрузки, G12 |
| A02 | Допущение | Возможно получить ограниченный snapshot/change feed Oracle без изменения критичного поведения. Способ, лицензии и стоимость не подтверждены, G13 |
| A03 | Допущение | Для производного хранилища найдётся поддерживаемый PostgreSQL-совместимый стек и ресурс. Продукт/размещение/HA не утверждены, G11/G14 |
| A04 | Ограничение доказательности | Предоставлены учебный фрагмент и стенограммы; отсутствуют весь репозиторий, DDL, execution plans, runtime config и метрики |

## Реестр пробелов

Пустое значение означает **неизвестно**, а не ноль и не разрешение принять типовое значение. G-идентификаторы связываются с gates roadmap/cutover.

| ID | Что уточнить | У кого / какое свидетельство | Заблокированное решение |
|---|---|---|---|
| G01 | SLA/SLO и допустимый downtime по checkout/payment/delivery/status; правила плановых работ | Спонсор + SRE/эксплуатация; договор/согласованный SLO | Утверждение доступности и production cutover |
| G02 | RPS/TPS, пики, сезонность, распределение каналов/заказов, active/history объёмы | Заказы + DBA + эксплуатация; профили/счётчики | Capacity и выбор topology/масштаба |
| G03 | Latency p95/p99, timeout budgets, допустимая нагрузка на Oracle | Заказы + платежи + эксплуатация; trace/DB baseline | Тайм-ауты, fallback capacity и canary границы |
| G04 | Consistency/семантика статусов, источники paid/refunded, частичные состояния | Заказы + финансы + логистика + поддержка; таблица переходов и cases | Пользовательская интерпретация и mapping |
| G05 | Допустимый lag read-view/аналитики, stale UI и период сравнения | Поддержка + аналитика + бизнес | Freshness gate и переход на новую проекцию |
| G06 | RTO/RPO по доменам и отказам; как устроены HA/backup и кто делает restore | Эксплуатация + DBA + владельцы; результаты восстановления | DR-дизайн и сроки rollback |
| G07 | Партнёрская идемпотентность, retries, late callbacks, cancel/refund semantics | Платежи/логистика + партнёры; API/контракты и инциденты | Извлечение write-интеграций/автоповторы |
| G08 | Baseline change lead time, ручных операций, стоимости контакта и target эффекта | Спонсор + support + PM/финансы | Доказательство ROI/успеха программы |
| G09 | Список SQL/отчётов, lineage, свежесть и стоимость каждого | Аналитика + DBA + финансы/маркетинг | Первый отчёт для переноса и архивирование |
| G10 | PII/ACL, сроки хранения, аудит, residency и допустимые поля журналов | ИБ + юристы + поддержка | Копирование production данных и доступ к read-model |
| G11 | Список запрещённых/разрешённых технологий, сроки и критерии импортонезависимости | IT-директор + закупки + ИБ | Выбор дистрибутива/поставщика и план выхода из Oracle |
| G12 | Первая внутренняя когорта/экран, owner UI, допустимый degraded mode | Поддержка + заказы + эксплуатация | Конкретный scope canary и fallback |
| G13 | Все writers/readers/tables/packages; CDC, consistent snapshot, log retention, transaction boundaries | Техлид + DBA + .NET/batch owners; DDL/roles/config/POC | Полнота проекции, SCN bootstrap, Oracle decommission |
| G14 | Доступная мощность, бюджет, команда, площадка нового контура и эксплуатация | IT-директор + инфраструктура; инвентарь/смета/on-call | Реальные сроки и размещение новых компонентов |
| G15 | Требования персонализации/партнёрских функций, приоритеты, данные и согласия | Спонсор + маркетинг + product + ИБ | Архитектура годовых сервисов |
| G16 | Интерфейс старого read-path, возможность route-only switch, runtime-версии/rollback, DNS/cache/session поведение | Заказы + support UI + эксплуатация; staging rehearsal | Воспроизводимый технический cutover |

Цели измерений фиксируются после baseline и согласования владельцем. До этого никакие «стандартные» 99.9%, 100 мс, N RPS, TTL, RPO 0 или процент canary не становятся требованиями RetailCore.
