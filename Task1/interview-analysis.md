# Анализ предоставленных интервью

Проанализированы E01–E05, сверены с E06/E07. Новые интервью по [сценариям](interview-scenarios.md) не проводились. «Подтверждено» ниже означает, что источник поддерживает гипотезу в указанной области; количественных измерений это не заменяет.

| Наблюдение / источник | Вопрос | Гипотеза | Результат проверки | Противоречие / предел | Вывод и следующий шаг |
|---|---|---|---|---|---|
| E01: «нет окна на большую миграцию» | Можно ли остановить платформу ради redesign? | H01: нужна поэтапная траектория | Подтверждено бизнесом | Целевой downtime/SLO не указан | C01/Q01; G01, plan с rollback и ранней ценностью |
| E01: устойчивость и запуск фич нельзя противопоставлять | Можно ли заморозить развитие на год? | H03: стабилизация не отменяет коммерческое развитие | Подтверждено | Скорость поставки и risk appetite не выражены числами | Параллельный discovery и ограниченные seams, G08/G14 |
| E01: критичны цена, доставка, подтверждение | Что опаснее менять? | H02: клиентское обещание ограничивает extraction | Подтверждено | «Менее критичный» read-view тоже может сообщить ложный факт | Не выводить paid/delivered из неподтверждённого статуса, G04 |
| E02: личный кабинет, письмо и оператор видят разное | Достаточен ли единый текущий status? | H04: нужна объяснимая модель по аспектам | Подтверждено | Различие может быть задержкой или разным срезом, а не дефектом всех систем | Нормализовать семантику/время; G04/G05; T02/T03 |
| E02: «где, что дальше, почему отклонение» | Какой результат важнее поддержки? | H09: read-only timeline даёт раннюю ценность | Поддержано, решение ещё не согласовано | Нельзя восстановить отсутствующую историю из одной current row | Показывать coverage/unknown; pilot owner G12 |

| E03: монолит «центральная точка» | Достаточно выделить существующие сервисы? | H07: оркестрация остаётся в ядре | Подтверждено E06 | E07 рисует блоки, но не доказывает deployable services | Checkout/payment/routing оставить на первом этапе |
| E03: fallback при недоступности promo; E06: ветка Optional.empty | Когда включается fallback? | Fallback всегда означает outage | **Не подтверждено кодом** | Фрагмент не содержит catch; пустой результат может иметь иной смысл | G04/G13: проверить PromoService и error handlers; не менять правило по догадке |
| E03: урезанные promo-правила | Эквивалентны ли расчёты? | Любой fallback сохраняет цену | **Опровергнуто интервью** для части заказов | Нет перечня веток и примеров сумм | Characterization fixtures и согласование коммерческого владельца |
| E03: длинные транзакции; E06 без transaction declaration | Внешний вызов находится в SQL-транзакции? | H10: граница не установлена | **Неизвестно** для метода | Интервью качественно о системе; фрагмент не доказывает атомарность/частичный commit | G13: configuration/repositories/trace, оценить locks без заявления доказанного rollback bug |
| E06: staging insert до manual review, delivery и payment | Может ли export увидеть преждевременный заказ? | H08: ранний side effect несёт риск | Порядок подтверждён; влияние **гипотеза** | Неизвестны commit и .NET eligibility filters | Проверить visibility/dedup; не включать параллельный новый writer |
| E04: разные REST, broker, polling, .NET | Есть ли единый интеграционный контракт? | Унифицированная шина уже решает ordering/dedup | **Опровергнуто** | Тип брокера и гарантии всех маршрутов неизвестны | Сначала контракт/инвентарь, потом один адаптер; G07/G13 |
| E04: повтор при молчании партнёра даёт дубли | Можно ли безопасно включить retries? | Retry любого запроса безопасен | **Опровергнуто** | Масштаб проблемы и idempotency API неизвестны | Не менять мутирующий поток до сверки контрактов |
| E04: routing в Java, config, Oracle, nightly SQL | Routing service — независимая граница? | Вынос routing прост | **Опровергнуто** | Нет полного dependency graph и split rules | Полный routing отложен; T05 сначала пограничный adapter |
| E05: SQL, staging, API, CSV и разные определения | Достаточно скопировать ORDERS в витрину? | Общая таблица даст единую семантику | **Опровергнуто** | Нет canonical model, cancel/refund retro-corrections разнятся | Словарь и provenance до отчётов; T04 |

| E03/E05: слабая корреляция и lineage | Можно ли считать журнал событий полным? | Доступна готовая полная история | **Опровергнуто** | Наличие отдельных logs не даёт полного order trace | T01; coverage map и честная граница истории |
| E00/E01: импортонезависимость без остановки | Нужно ли заменить Oracle в первой волне? | Полная замена — первый обязательный этап | **Не следует из источников** | Нет целевого списка продуктов/сроков | G11; новые производные модели и последующий аудит PL/SQL |

Основные противоречия не разрешаются голосованием источников: формальная lifecycle против фактических веток; внешняя независимость .NET против shared tables; «fallback на outage» против `Optional.empty`; желание общей правды против разных бизнес-срезов. Следующий результат discovery — примеры заказов, DDL/конфигурации и trace, подтверждающие или уточняющие каждую гипотезу. Обещания SLA, latency, RPO/RTO и freshness остаются пробелами [G01–G06](requirements.md).
