# AS-IS — факты, связи и ограничения анализа

## 1. Восстановленный контекст

[Схема drawio](as-is.drawio), [PNG](as-is.png). Собственные web/mobile-каналы и маркетплейсы передают заказы в Java-ядро. Checkout, Order Processing, Pricing/Promo, Payment Orchestration, Delivery Routing и Status Management — логические области внутри монолита, не доказанные независимые сервисы. Код и E03 подтверждают, что оркестрация остаётся в центре.

Oracle обслуживает транзакционные данные, правила/PLSQL, технические поля, статусы, staging и часть отчётов. .NET и Python имеют прямую зависимость от неё; наличие процессов вне JVM не доказывает владение своими данными. Асинхронный контур неоднороден: broker, polling, batch, CSV. По E07 нельзя установить продукт брокера, deployment topology или end-to-end гарантии.

Склад/сервис наличия добавлен на уточнённую схему по E03/E04: в E07 он отсутствует. Синхронная зависимость наличия известна из интервью, но API, владелец и фактический маршрут неизвестны. Promo service показан отдельно по вызову E06; его размещение/владелец не установлены. Ручные и batch writers явно указаны: иначе диаграмма создавала бы ложное впечатление единого владельца статусов.

| Связь | Поток / режим | Доказательство и предел |
|---|---|---|
| Каналы/marketplaces → ядро | Create/update и чтение статуса, sync | E03/E07; методы/auth/retries каналов неизвестны |
| Ядро ↔ Oracle | SQL/repository/PLSQL: order, price/routing, statuses, staging | E06 конкретен, E03 объясняет более широкую зависимость |
| Ядро → promo service | `calculateDiscount`, результат Optional | E06; «нет скидки» и «сервис упал» нельзя считать одной семантикой |
| Ядро → логистика / PSP | `reserveSlot`, затем `createSession` | E06; callbacks, HTTP-коды и транзакционный охват не показаны |
| Ядро → наличие/склады | Синхронная зависимость и резервы | E03/E04; фрагмент E06 не содержит этой реализации |
| Ядро ↔ .NET | Staging/shared Oracle tables плюс часть async | E03/E04/E06/E07; фактические filters/claim/ACK неизвестны |
| Batch/admin → Oracle/statuses | Retry, корректировки, региональные правила | E02–E04; права, расписания и точный набор writers нужно инвентаризировать |
| Python/BI → Oracle | SQL/выгрузки и смешанные источники | E05; нет AWR/SQL plans и количественного вклада нагрузки |

## 2. Что видно в Java-фрагменте

Номера строк относятся к сохранённому [E06](../sources/OrderProcessingService.java). Полный класс не скомпилировать без зависимостей; анализ статический. Схема E07 не подменяет код, а код не подменяет всю production-систему.

| Строки | Подтверждённое поведение | Риск / что нельзя утверждать | Проверка |
|---|---|---|---|
| 55–66 | Создаёт `NEW`, берёт item prices/quantity из command, суммирует BigDecimal | Проверки цены/количества могут быть выше; фрагмент не доказывает отсутствие валидации или доверие внешнему клиенту | Входной API, price authority, validation |
| 68–74 | Ветви MARKETPLACE +49 и FAR_EAST +350 | Сборы зашиты в код; эти числа не новое бизнес-требование | Подтвердить тарифы, порядок их применения и канал |
| 76–87 | При включённых промо вызывает PromoService; при empty вызывает Oracle package | Fallback на **empty**, не показан catch на outage; E03 описывает более широкое поведение | Adapter, exception path, golden calculations |
| 90–96 | Save order, затем insert INT_ORDER_EXPORT | Возможна ранняя экспортная запись, но видимость зависит от commit и .NET filters | Transaction configuration, staging consumer |
| 98–105 | FindRule или default; manual review возвращает ранний результат | Default route может иметь бизнес-смысл, неизвестный без контракта | Матрица маршрутов и manual states |
| 107–120 | Sync reserveSlot; failure → DELIVERY_PENDING, SQL retry_after +10 минут, accepted deferred | Retry 10 минут — факт фрагмента, не SLO. Unknown outcome/повтор не описаны | Контракт партнёра и batch-обработчик |
| 123–127 | Sync createSession; false → PAYMENT_PENDING и exception | Судьба ранее записанных данных и резерва зависит от транзакции/handler; нельзя доказать partial commit по этому методу | Commit/rollback, компенсации, внешний статус |
| 130–136 | CONFIRMED, SQL update payment_session_id/partner, возврат redirect URL | `CONFIRMED` здесь не означает захваченные деньги. Обновления разными API требуют общей семантики | Определение confirmed/paid, atomicity и callbacks |

В методе отсутствует видимый бизнес-ключ идемпотентности, но он может существовать выше/ниже. Нет аннотации транзакции, однако transaction interceptor/config или репозитории могли её задать. Об утечках соединений, отсутствии HA, SQL injection, неограниченных retries или конкретном p99 по фрагменту заявлять нельзя. `LegacySqlExecutor` принимает placeholders, а не демонстрирует конкатенацию пользовательского SQL. Неиспользованный `dataSource` — частная деталь примера, не главный драйвер трансформации.

## 3. Матрица реальных исходов

| Сценарий | Что наблюдается | Что остаётся неизвестным |
|---|---|---|
| Обычная ветка E06 | Цена → save/staging → slot → payment session → CONFIRMED | Созданная сессия не доказывает факт оплаты; capture/authorisation не показаны |
| Manual review | После staging задаётся WAITING_MANUAL_REVIEW и метод возвращает результат | Какие external consumers уже получили заказ и кто снимает review |
| Delivery failure | DELIVERY_PENDING + DB retry; method возвращает accepted | Кто и как разрешает timeout/дубликат, как затем создаётся оплата |
| Payment creation false | PAYMENT_PENDING + exception после успешного reserveSlot | Commit/rollback, компенсация слота, возможный уже созданный внешний ресурс |
| Split/cancel/refund | Наблюдается в E02/E03/E04, в E06 не реализовано | Item/shipment-level state machine и financial facts |
| Ручное исправление/batch | Несколько writers по E02–E04 | Полнота истории и последствия прямой смены technical state |

Резервирование товаров нельзя отождествлять с показанным reserveSlot доставки. Один request path не исчерпывает lifecycle. Историю команды должны воспроизвести по case IDs, временным отметкам и источникам данных; порядок чужих timestamps сам по себе не доказывает причинность.

## 4. Ограничения для изменений

| Зона риска | Механизм влияния | Безопасный следующий шаг |
|---|---|---|
| Синхронные зависимости | Время внешней системы влияет на checkout; результат timeout неоднозначен | Tracing и контракт исхода, без автоматического async-переноса клиентского обещания |
| Oracle coupling | Бизнес-логика и обмен находятся за пределами Java-классов | DDL/packages/jobs/access inventory и characterization, не механическая смена JDBC URL |
| Распределённые статусы | Несколько писателей, разные аспекты и snapshots времени | Observation model с provenance; единое управление transition позднее |
| Аналитика на OLTP | Общий CPU/IO/locks/pool может усиливать пики | Профиль самых дорогих запросов и пилот одного read consumer |
| Ручные исключения | Организация компенсирует неполные контракты | Сохранить recovery actions, добавить audit и объяснение |
| Мало инфраструктурного резерва | Shadow/backfill тоже могут ухудшить production | G02/G03/G14: лимиты чтения и capacity gate до начала копирования |

## 5. Оценка исходных артефактов

E07 полезна как карта поиска, но смешивает уровни: actor/system context, внутренние модули Java и storage на одном листе. Она не отражает всех канальных правил, наличия, сторонних promo-вызовов, manual/batch transitions и фактических DB-транзакций. Уточнённая диаграмма поэтому называется **контекст и границы подсистем**, а не строгая C4 L1 с каждым модулем как системой.

Интервью дают перекрёстное подтверждение shared DB, неоднородных статусов и ручной работы. При этом выборки инцидентов/частот отсутствуют. Код подтверждает отдельные механизмы, но не production-version и не полное поведение. Следующие обязательные свидетельства: DDL/PLSQL, config/transaction interceptors, writer/read inventory, logs/traces, partner contracts, support cases, query plans и результаты backup restore. Полная картина через три месяца считается достигнутой только после такой проверки и подписи владельцев, а не после рисования новой схемы.
