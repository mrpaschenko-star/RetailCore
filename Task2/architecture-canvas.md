# Architecture Canvas — RetailCore

Обзор объединяет бизнес, систему, качества, ограничения и риски в формате Software Architecture Canvas. Структура адаптирована к кейсу; ориентир из задания — [arc42 Architecture Communication Canvas](https://canvas.arc42.org/architecture-communication-canvas). Это canvas текущего состояния и направлений решений, а не утверждение готовой целевой платформы.

| Блок | Содержание |
|---|---|
| **Бизнес и ценность** | Сохранить выполнение заказа и клиентское обещание, ускорить предсказуемые коммерческие изменения, снизить ручные межкомандные разборы. Три месяца — достоверная диагностика и основа перехода; год — новые сервисы и партнёрские сценарии. E00/E01 |
| **Пользователи и стейкхолдеры** | Клиенты web/mobile/marketplace, поддержка, цифровые продажи, заказы, логистика, платежи/финансы, аналитика, DBA, инфраструктура, ИБ и внешние партнёры. [Карта](../Task1/stakeholders.md) |
| **Функции** | Checkout, цена и промо, создание/обработка, наличие и резервы, платёжная сессия, маршрутизация/доставка, статусы/ручной recovery, партнёрские интеграции, отчёты. Различаются каналы и исключения; F01–F08 |
| **Граница системы и окружение** | Внутри: собственные каналы, Java-ядро с Oracle, .NET-интеграции, Python jobs, admin/support. Снаружи платформы: клиенты, операторы, marketplaces, PSP, службы доставки и склад/наличие; BI — внутренний потребитель вне operational boundary. Границы deployment/ownership требуют подтверждения |
| **Архитектурная форма** | Гибридный монолит и сервисы; синхронные вызовы, async/batch и shared-table exchange. Oracle одновременно OLTP, PL/SQL rules, integration staging и источник аналитики. E03–E07 |
| **Ключевой сценарий** | Канал → монолит → price/promo → save + staging → delivery route/manual review → reserve slot → payment session → confirmed. E06 задаёт одну ветку; весь lifecycle и каналы шире фрагмента |
| **Качества** | Непрерывность, корректное объяснение состояний, предсказуемая нагрузка, управляемое восстановление, безопасность данных, наблюдаемость и изменяемость. Метрики определены, численные требования отсутствуют: Q01–Q09, G01–G16 |
| **Данные и владение** | Десятки TB; current order, status history, technical fields, reference/routing tables, PL/SQL, batch corrections. Согласованный business-event stream отсутствует; current row не равна полной истории. Связь paid/refund с PSP требует уточнения |
| **Ограничения** | Физический DC, ограниченная виртуализация, мало headroom; неполные документы, скрытые связи и носители знания; поэтапность и запрет большой остановки. Бюджет, staffing, cloud policy и допустимые продукты неизвестны |
| **Проблемы и риски** | Цена/промо/status fragmentированы; Oracle coupling; timeout/повторы партнёров; ложное обещание доставки; ручной recovery; тяжёлая аналитика и неполный lineage; риск утратить прозрачность при миграции |
| **Измерения и доказательства** | Golden scenario set по каналам/исключениям, map writers/readers, traces и SQL waits, причины обращений, provenance отчётов, нагрузочный/restore baseline. Источники E00–E07 подтверждают качественную картину, а не SLO |
| **Направление первого изменения** | Сначала наблюдаемость и согласование semantics, затем проверенный capture и внутренняя read-only история заказа. Критичные writes остаются в Java/Oracle. Далее один отчёт и одна подходящая интеграционная граница, после отдельных gates |
| **Открытые решения** | Источники фактов, lag/consistency, RTO/RPO, capacity, snapshot/CDC feasibility, критерии импортонезависимости, owner нового контура, область canary. [Реестр пробелов](../Task1/requirements.md) |
